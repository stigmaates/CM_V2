# Пульс гостя · stage v1

Отдельная вкладка владельца и совладельца: `/owner/guest-pulse`. Администратор
видит её в режиме просмотра выбранного клуба. Реальные отправки и начисления
выполняются существующим CRM-модулем после действия пользователя.

## Что реализовано

- Независимые Health / Value / Engagement, Lifecycle, причины, динамика H за 7/14/30 дней.
- Диапазоны H/V/E; круговая диаграмма; семь взаимоисключающих типов, счётчики X/Y.
- Панель гостей справа (по 10 на странице), подробная карточка и история переходов.
- Личная медиана предыдущих 30 дней при наличии 7 снимков; диапазон отклонений,
  направление изменения и все сработавшие показатели. Нижний блок независим от верхних фильтров.
- Восемь быстрых сегментов из постановки, включая резкое снижение Health при ещё активном статусе.
- Передача всей выборки, а не текущей страницы, в существующую CRM-форму сообщений/КБ/жетонов.
  Выборка фиксируется на сервере на 2 часа и ограничивается клубом и пользователем.
  Повторная отправка той же выборки возвращает существующий mailing_id.
- Ежедневная история, восстановление 30 прошлых дней и атомарный пересчёт клуба.

## Согласованные продуктовые уточнения

1. Гости без завершённых визитов не показываются. Один визит всегда даёт NEW и Health=NULL,
   независимо от его давности. При двух-трёх визитах оценка помечается предварительной.
2. В Langame-сессиях нет признака платного времени. Value использует **игровые часы**
   и **пополнения**, а не заявляет платные часы или бухгалтерскую выручку.
   Среднее — пополнения за 90 дней / визиты за 90 дней; ноль при отсутствии визитов в окне.
3. Streak — последовательные календарные дни осмысленных действий Кибер Бонус
   в часовом поясе клуба. Если сегодня действия ещё не было, продолжается вчерашняя серия.
   Посещения клуба сами по себе не увеличивают Engagement.
4. История восстанавливается по сохранённым событиям с отсечением будущих данных.
   Исторический Engagement **приблизительный**: Telegram считается подключённым
   начиная с первой сохранённой авторизации либо осмысленного действия. Полной истории
   привязок/отвязок в старой БД нет. Оценки и baseline с такими снимками имеют пометку.
5. Health=NULL проходит полный диапазон 0–100, но не проходит суженный диапазон Health.
6. Percentile: доля участников базы сравнения со строго меньшим значением (одинаковые
   значения получают одинаковый ранг). База — гости текущего клуба с >=2 визитами за 90 дней.
   Если базы сравнения нет, Value=NULL. Веса доступных компонентов нормализуются.
7. При двух старых визитах без достоверных компонентов возможен Lifecycle
   `INSUFFICIENT_DATA`, отображаемый как «Недостаточно данных».

## Слои данных

`app/services/visits.py` — общий слой нормализации, используемый и пересборкой
`user_portrait`, и «Пульсом гостя». Разрыв до двух часов объединяет сессии в один
визит. Незавершённые/некорректные сессии исключаются. Игровые часы считают объединение
времени сессий: без перерывов и без удвоения пересекающихся сессий.

Текущий полный набор CRM-признаков и объяснений хранится в `guest_pulse_current.detail_json`;
числовые H/V/E, lifecycle и тип аудитории имеют отдельные колонки.
В `user_portrait` проецируются H/V/E, lifecycle, ΔH14 и время пересчёта. Старый `crm_type`
не заменяется, поэтому существующие кампании сохраняют прежнюю семантику.

`guest_score_history`: один неизменяемый снимок на `(club_id, guest_id, snapshot_date)`.
Компоненты, причины и признаки находятся в `detail_json`. Повторный backfill заполняет
пропуски, но не перезаписывает живые или ранее сохранённые снимки.
`guest_lifecycle_events`: переходы с причиной и Health до/после; восстановленные события помечены.
Снимки хранятся без автоматического удаления; baseline использует только последние 30 дней,
исключая сегодня. Восстановление использует ещё 15 дней прогрева для реактивации.

Времена БД трактуются как UTC. Расчётные окна, дни, streak и snapshot_date — по зоне клуба.
Value всегда пересчитывается для всего клуба: изменение одного гостя может изменить ранги остальных.

## Пересчёт

Миграция `0028_guest_pulse` добавляет 30 триггеров (INSERT/UPDATE/DELETE) на источники
визитов, пополнений, Telegram, миссий, колеса, кейсов, конвертаций и призов.
Триггер только увеличивает поколение очереди `guest_pulse_dirty` в транзакции источника.
Rollback игрового действия откатывает и очередь. Для миграции нужны права CREATE TRIGGER.

Stage-таймер запускает обработчик через 15 секунд после завершения предыдущего запуска.
Это событийный асинхронный пересчёт: он не задерживает выдачу наград.
В 04:00–05:00 местного времени клуба выполняется ежедневный пересчёт и снимок;
при простое сервиса пропущенный запуск выполняется после восстановления.
Внутридневные изменения обновляют текущие оценки, сохраняя уже записанный снимок дня.

Блокировка клуба через GET_LOCK изолирована именем БД. Ошибка одного клуба не останавливает
обработку других. Ошибка откатывает снимки, события и текущие оценки; очередь остаётся
для повторной попытки. Изменения источников во время расчёта сохраняются следующим поколением.

```bash
venv/bin/python scripts/rebuild_guest_pulse.py --backfill
venv/bin/python scripts/rebuild_guest_pulse.py --club-id 2 --force
venv/bin/python scripts/check_guest_pulse.py
```

`--backfill` не отправляет сообщений и не начисляет наград. Старые события, которые
не были сохранены либо были удалены до внедрения, восстановить невозможно.

Пороги системы задаются переменными `GUEST_PULSE_*` в `app/config.py`.
Названия/порядок типов — справочник `AUDIENCES` в `guest_pulse_scores.py`.
После изменения порогов выполнить `--force` для текущих оценок; история остаётся прежней.

## Выкладка только на stage

```bash
(
set -euo pipefail
cd /root/cm_stage/CM_V2
git switch product-readiness-from-stage
git pull --ff-only origin product-readiness-from-stage
bash scripts/backup_mysql.sh
venv/bin/python scripts/migrate.py
venv/bin/python scripts/rebuild_guest_pulse.py --backfill
venv/bin/python scripts/check_guest_pulse.py
venv/bin/python -m compileall -q app scripts migrations
install -m 644 deploy/systemd/clubmodule-stage-guest-pulse.service /etc/systemd/system/
install -m 644 deploy/systemd/clubmodule-stage-guest-pulse.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now clubmodule-stage-guest-pulse.timer
systemctl restart clubmodule-stage.service
systemctl is-active clubmodule-stage.service clubmodule-stage-guest-pulse.timer
venv/bin/python scripts/migrate.py --dry-run
git rev-parse --short HEAD
)
```

После ошибки миграции остановиться, не перезапускать web. Боты не изменялись.
Production-ветка и сервер не входят в этот релиз.

## Проверка на стенде

- Сверить по одному гостю: один визит; постоянник; пропавший; вернувшийся. Исключить гостей без визитов.
- Проверить диаграмму, X/Y, диапазоны, карточку, смену страниц и мобильный экран.
- Сравнить несколько дневных H/V/E с сохранёнными визитами/пополнениями на соответствующие даты.
- Создать новое тестовое игровое событие, дождаться таймера и проверить Engagement.
- Проверить, что в форме CRM остаётся полная выбранная аудитория; отправку делать только тестовому гостю.
- Проверить два клуба с одинаковым guest_id и повторные обновления таймера.
- Прочитать `journalctl -u clubmodule-stage-guest-pulse.service -n 30 --no-pager` при ошибке.

## Автоматические проверки

Тесты формул и API запускаются обычным pytest. Storage-тесты по умолчанию используют
временную SQLite с адаптацией диалекта: это проверка логики и транзакционного отката,
а не доказательство поведения MySQL-триггеров/блокировок.

Для **отдельного тестового MySQL** (не рабочего сервера БД) предусмотрен:

```bash
GUEST_PULSE_TEST_SOCKET=/path/to/test-mysql.sock \
  venv/bin/python -m pytest tests/test_guest_pulse_storage.py -q
```

Каждый тест создаёт и удаляет случайную базу `guest_pulse_test_*`.
Локальный MySQL 9.3 упал при инициализации SIGSEGV; нативная проверка на нём не состоялась.
UI проверен Chromium на синтетических данных: диапазоны, выбор типа, карточка,
закрытие Escape и мобильное окно 390 px.
