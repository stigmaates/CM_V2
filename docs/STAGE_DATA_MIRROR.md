# Обновление stage из production без отправок

Stage: `/root/cm_stage/CM_V2`, ветка `product-readiness-from-stage`.
Production: `/root/cm_v2/CM_V2`; используется только для чтения базы.

## Установка

Запускать на сервере от root:

```bash
(
set -euo pipefail
cd /root/cm_stage/CM_V2
git pull --ff-only origin product-readiness-from-stage
venv/bin/python scripts/setup_stage_mirror.py --apply
)
```

Без `--apply` установщик выполняет только проверки. Он проверяет разные имена
баз, совместимость таблиц и реальные пути systemd-служб. Затем при установке:

1. Создаёт локальный файл `.stage-no-outbound`, блокирующий исходящие сообщения.
2. Сохраняет и отключает найденные задания stage в root crontab, `/etc/crontab`,
   `/etc/cron.d`, а также stage-службы и их таймеры. Задания резервного копирования
   остаются. Задания production не меняются; смешанные пути вызывают отказ.
3. Останавливает stage web и ботов, проверяет отсутствие работающих Python-задач
   stage и сохраняет резервную копию stage в `backups/mirror-setup-*`.
4. Копирует бизнес-таблицы production одной транзакцией в stage, восстанавливает
   историю HVE по доступным событиям production, пересчитывает портреты и HVE.
5. Запускает stage web и `clubmodule-stage-data-mirror.timer`.

Новый цикл начинается через 5 минут после завершения предыдущего. Копируются
гости, сессии, операции, пополнения, Telegram-привязки, действия и награды
Кибер Бонус, настройки и другие бизнес-таблицы production. Stage `.env` и схема
не заменяются. История HVE и служебные записи фоновых задач stage сохраняются
при регулярных запусках. При первоначальной установке история HVE пересоздаётся.
Изменения бизнес-данных, сделанные вручную на stage, будут заменены очередной копией.

Очереди рассылок также копируются, но обработчики и Telegram-транспорты
блокируются локальным стоп-файлом. Боты не запускаются. Не удалять стоп-файл
и не включать старые обработчики: stage содержит реальные очереди production.
Не использовать старый `refresh_stage_from_production.sh` для этого режима.

Копирование не выполняет DDL и TRUNCATE: сбой до commit откатывает замену всех
таблиц. Ошибка пересчёта после commit не отменяет уже скопированные бизнес-данные;
следующий успешный запуск повторяет пересчёт. Файл `.stage-mirror-state.json`
обновляется только после завершения копирования и всех проверок.

## Проверка и ручное обновление

```bash
systemctl is-active clubmodule-stage.service clubmodule-stage-data-mirror.timer
systemctl list-timers clubmodule-stage-data-mirror.timer --no-pager
journalctl -u clubmodule-stage-data-mirror.service -n 30 --no-pager
cat /root/cm_stage/CM_V2/.stage-mirror-state.json
```

Для внеочередного обновления:

```bash
systemctl start clubmodule-stage-data-mirror.service
```

Остановить регулярное обновление, сохранив блокировку отправок:

```bash
systemctl disable --now clubmodule-stage-data-mirror.timer
```

Если установщик остановился после остановки stage, web остаётся остановленным.
Нужно устранить показанную причину и повторить установку. Не включать ботов и
рассылки для восстановления доступности веб-интерфейса. Исходные cron-файлы,
список остановленных служб и SQL-бэкап находятся в каталоге резервной копии;
`manifest.json` сопоставляет сохранённые cron-файлы исходным путям.

Локальные тесты проверяют откат через SQLite-адаптер и блокировку обработчиков.
Совместимость с фактической схемой MySQL проверяется установщиком на сервере;
первый успешный перенос и журнал нужны для подтверждения работы на стенде.

## Продолжить после прерывания пересчёта

Если в журнале уже есть `Business data committed atomically`, бизнес-данные
сохранены. После Ctrl+C на пересчёте можно завершить установку без повторного
копирования и без очистки уже восстановленной части HVE:

```bash
venv/bin/python scripts/setup_stage_mirror.py --apply --resume-after-copy
```

Этот режим предназначен только для подтверждённого завершения копирования.
Пересчёт повторяется; каждые 30 секунд выводится сообщение, что процесс ещё
работает. Это индикатор работы процесса, а не процент готовности.

Для временного восстановления веб-интерфейса после прерванной установки:

```bash
systemctl start clubmodule-stage.service
systemctl is-active clubmodule-stage.service
```

Запуск только веб-службы не снимает локальную блокировку отправок. До окончания
пересчёта HVE может быть неполным. Продолжение установки снова кратковременно
останавливает веб-службу и запускает её после успешных проверок.
