# Управляемое выпадение

Настройки → Управляемое выпадение (рядом с управлением гостями).
Доступ: владелец, совладелец и разрешённый существующим механизмом режим
просмотра клуба администратором. Сотрудник ресепшена доступа не получает.

## Использование

1. Найти гостя по номеру в базе текущего клуба. Форматы +7 / 8 / 10 цифр
   сопоставляются, пробелы и разделители не мешают поиску.
2. Если номер встречается у нескольких гостей, выбрать нужную карточку по ФИО и ID.
3. Выбрать активный кейс или включённое колесо и активный приз.
   Приз с нулевым обычным весом тоже можно назначить.
4. Назначить выпадение. Для одного гостя допускается одно ожидающее назначение
   на конкретный кейс или колесо. Для замены сначала отменить прежнее.
5. Следующее успешное открытие выбранной механики выдаст назначенный приз.
   После этого снова действуют обычные веса. Открытие другого кейса не расходует назначение.

Стоимость открытия, начисление КБ/жетонов и создание заявки на физический приз
проходят через существующую логику. Для гостя используются прежние ответы API,
анимация и история призов. Данные об управляемом назначении в гостевой API не добавляются.

История показывает 5 последних назначений всего клуба. «Показать всю историю»
открывает полный список страницами по 50 записей. Записи содержат снимки ФИО,
телефона, названий кейса/приза и автора назначения, время в часовом поясе клуба,
статус, номер состоявшегося открытия. Ожидающее назначение можно отменить.
Назначения, отмены и результаты сохраняются; удаление кейса или гостя не удаляет историю.

## Атомарность и пограничные случаи

- `managed_drops` создаётся миграцией `0027_managed_drops`.
- Уникальный индекс запрещает два ожидающих назначения одной механики для одного гостя.
- Уникальный ключ формы предотвращает повторное назначение при повторной отправке
  исходной формы, в том числе после уже состоявшегося открытия.
- Запись назначения блокируется через `SELECT … FOR UPDATE`. Употребление назначения,
  открытие, списание и награда фиксируются одной транзакцией. Ошибка до commit
  оставляет назначение ожидающим и откатывает списание.
- Баланс блокируется и при бесплатном кейсе для одинакового порядка блокировок.
- Недостаток жетонов не расходует назначение.
- Выбор и возврат фактического приза колеса выполняются в одной операции сохранения;
  API не показывает предварительно выбранный случайный приз.
- Если назначенный предмет удалён/выключен, при успешном открытии с другим доступным
  призом назначение отмечается «Приз недоступен» и используются обычные вероятности.
  Когда открыть механику вообще нельзя, назначение остаётся ожидающим; его можно отменить.
- Тестовый режим гостя не расходует управляемые назначения.
- Назначение само по себе не начисляет наград, не запускает открытие и не отправляет сообщения.

## Проверки и обновление

Локальные тесты `tests/test_managed_drops.py` проверяют назначения, отмены, защиту
клубов, повторную форму, сбои начисления, физические призы и одновременные открытия.
По умолчанию используется временная SQLite с блокировкой записи всей базы.
Для проверки настоящих MySQL-блокировок предусмотрен запуск с переменной
`MANAGED_DROPS_TEST_SOCKET`, указывающей на отдельный локальный тестовый MySQL:

```bash
MANAGED_DROPS_TEST_SOCKET=/path/to/test-mysql.sock venv/bin/python -m pytest -q tests/test_managed_drops.py
```

Этот режим создаёт и удаляет отдельные базы `managed_drop_test_<uuid>` через локальный
root без пароля. Он не использует параметры БД приложения. Запускать только против
специально выделенного тестового MySQL.

Обновление stage после получения коммита:

```bash
(
set -e
cd /root/cm_stage/CM_V2
git switch product-readiness-from-stage
git pull --ff-only origin product-readiness-from-stage
bash scripts/backup_mysql.sh
venv/bin/python scripts/migrate.py
systemctl restart clubmodule-stage.service
systemctl is-active clubmodule-stage.service
)
```

Миграция обязательна до перезапуска web. На stage проверить назначение для обычного
тестового аккаунта: первое открытие — назначенный приз, второе — обычное. Режим
«Открыть как гость» с `guest_test_mode` намеренно не проверяет принудительную выдачу.
Перед production также проверить отмену и историю в выбранном часовом поясе клуба.
