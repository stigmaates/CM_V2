# Команда

Вкладка справа от «Настройки». Два независимых периода: регистрации в клубе/модуле
и когорта зарегистрированных в Langame для повторных визитов. «Неделя» — текущая
календарная с понедельника, «Месяц» — текущий календарный; обе даты включаются.
Когорту определяет `guests.date_insert`, а визиты учитываются до текущего времени,
даже если произошли после выбранного периода. Завершённые игровые сессии с перерывом
до 2 часов объединяются общим алгоритмом «Пульса». 1→2 = второй/первый,
2→3 = третий/второй; отдельно показаны все регистрации, включая ещё не посетивших.

Атрибуция регистрации: единственная смена, включающая её время, `[start, stop)`.
Нет смены или несколько — «Не определён». Старые сотрудники остаются по истории
смен. Работа сотрудника в текущем клубе определяется `users.work_point`, историческая —
сменами этого клуба. Смена открыта при `date_stop=null`; незакрытые старые смены могут
создавать пересечения, такие регистрации не назначаются произвольно.

`module_registrations` хранит первую регистрацию на пару club_id/guest_id.
Триггер AFTER UPDATE guests фиксирует первую привязку Telegram (NULL/0 → ID) в UTC,
без зависимости от приветственной награды; перепривязка не перезаписывает дату.
История восстанавливается по MIN(created_at) подтверждённых токенов/первых наград и
reviewed_at одобренных заявок. Восстановленные даты приблизительные: награда могла
быть выдана позже, а токен создан раньше завершения регистрации. Если свидетельств
нет, дата NULL: время первого наблюдения не выдаётся за дату регистрации.

После включения первый успешный Telegram-link атомарно создаёт точную запись
`module_registrations`. История до включения механизма остаётся приблизительной или
без известной даты и отмечается знаком ≈.

Время сырого Langame API интерпретируется по текущему соглашению приложения как UTC
и переводится в часовой пояс клуба (как в Guest Pulse). Спецификация не обозначает
часовой пояс строк; до использования отчёта для выплат нужно сверить реальные начала
смен и регистрации с интерфейсом Langame. История/API-доступ тоже проверяются первым
импортом; нельзя обещать полное покрытие только на основании OpenAPI.

## Данные Langame

`sync_team.py` делает только GET `/clubs/list`, `/users/list`, `/working_shifts/list`.
Смены читаются со всех страниц, затем вместе с сотрудниками заменяются одной локальной
транзакцией. Ошибка любой страницы сохраняет предыдущие данные и видимый статус ошибки.
Клуб сопоставляется по club_secret, либо как единственный клуб ответа. Нельзя считать
локальный club_id равным Langame ID без проверки. Для явного соответствия:

```bash
venv/bin/python scripts/sync_team.py --club-id LOCAL_ID --langame-club-id LANGAME_ID
```

Production-таймер обновляет команду раз в 15 минут. Сбой API не отменяет предыдущий
успешный набор данных и отображается на вкладке. Кнопка «Обновить отчёт» перечитывает
локальные данные и не запускает API/фоновые записи внутри веб-запроса.

## Подготовка к production-развёртыванию

Перед включением нужны резервная копия БД и проверка на копии production-данных.
Импортёр использует только GET-запросы к Langame и локально обновляет кэш команды;
он не отправляет сообщения гостям.

```bash
(
set -euo pipefail
cd /root/cm_v2/CM_V2
bash scripts/backup_mysql.sh
git pull --ff-only origin <утверждённая-release-ветка>
venv/bin/python scripts/migrate.py
venv/bin/python scripts/sync_team.py --club-id LOCAL_ID --langame-club-id LANGAME_ID
venv/bin/python scripts/check_team.py
install -m 644 deploy/systemd/clubmodule-team-sync.service /etc/systemd/system/
install -m 644 deploy/systemd/clubmodule-team-sync.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now clubmodule-team-sync.timer
systemctl restart clubmodule.service
)
```

Перед первым регулярным запуском для каждого клуба нужно подтвердить соответствие
локального `club_id` и Langame ID. Работу импорта защищает отдельная блокировка.
Если миграция завершилась ошибкой, остановиться и устранить её по выводу.
