# Gizmo v3 — пилот Next, Уфа

Пилот предназначен только для `/root/cm_stage/CM_V2` и отдельной базы stage.
Прод не меняется. Секретов в репозитории нет. Обслуживание пилота остаётся выключенным;
рассылки, награды, запись денег в Gizmo и периодический импорт не включаются.

## Проверено на API 6 октября 2026

Gizmo 3.0.92, HTTPS с проверенным сертификатом и именем `gizmo.local`,
филиал `NextClub`, branch ID 1, один филиал в ответе. Его timezone API возвращает
`Asia/Yekaterinburg`. Ключ передаётся через X-API-KEY. С действующим ключом
`system/version`, `branches`, `hosts`, `users`, `paymentmethods`,
`deposittransactions`, `sessions`, `usersessions` возвращают успешные ответы.
Следующие страницы hosts/users/deposittransactions/sessions/usersessions также проверены.
Реальный `nextCursor` — непрозрачная строка, хотя OpenAPI описывает объект.
`reports/sessionslog` возвращает HTTP 403 даже с новым ключом. Причина политики
доступа не установлена; импорт использует два доступных метода сессий.

## Единый формат

| Gizmo | Таблица модуля | Правила |
|---|---|---|
| users, Type=0, Model.Id | guests | guest_id = внешний ID, область уникальности club_id + guest_id |
| FirstName/LastName, MobilePhone/Phone | guests.fio/phone | Нормализация телефона, не связывать гостей разных клубов по ID/телефону |
| RegistrationDate/BirthDate | guests.date_insert/birth_date | Время регистрации UTC; день рождения календарной датой |
| hosts.Model.Id/Name/Number | club_pc_names | Стабильный uuid `gizmo:<ID>`; ручные названия и порядок не перезаписывать |
| sessions + usersessions | guest_sessions | JOIN sessions.usageSessionId = usersessions.id, проверить userId; ПК из hostId |
| sessions.id/startTime/endTime | guest_sessions.id/date_start/date_stop | ID учётной сессии; UTC; не выдумывать окончание активной сессии |
| deposittransactions | guest_balance_topups | Только Deposit, выбранный branch, явно сопоставленные денежные способы оплаты |

События хранятся как DATETIME в UTC (как ожидает `guest_pulse.load_sources`);
локальное время Уфы используется при показе/расчёте пульса. Не прибавлять 5 часов в БД.
Sex — числовое поле на реальном сервере, но значения не объяснены в спецификации:
пол пока не выводим из номера. Type=1 users — общие/гостевые аккаунты, не персональные
CRM-профили. Удалённым/отключённым зарегистрированным пользователям телефон не импортируем.

Cash (-1) и Credit Card (-2) найдены в справочнике. Points (-4) и Deposit (-3)
не трактуем как новые деньги гостя. Для запуска нужно явно указать денежные методы.
Charge/Withdraw/Credit и isVoid не превращаются в положительное пополнение.
Отмена isVoided обновляет сумму ранее импортированного пополнения до нуля.
Повтор периода нужен для обнаружения отмен; постоянная сверка старых отмен ещё не включена.

Не импортируем `operations_log`: экономический смысл всех списаний и продаж ещё
не сопоставлен с категориями Langame. Нельзя считать пустой журнал отчётом о нулевых продажах.
Не используем изменение баланса в качестве пополнения. Внешние начисления не реализованы.

## Изоляция

`clubs.integration_provider`: langame (default для существующих) или gizmo.
`integration_ready=0` блокирует включение обслуживания Gizmo из админки.
Система не редактируется переключателем для уже заполненного клуба.
`club_integrations` хранит внешний филиал, источник/период и время импорта, без API-ключа.
Смена источника, филиала или пространства ID сессий после импорта запрещена.

Langame jobs явно пропускают Gizmo. Stage mirror сохраняет записи клубов с другим
provider в таблицах с club_id. При пересечении club_id с продом останавливается до
удаления данных. Суррогатные id pilot topups/PC names выделяются отрицательными, чтобы
новые положительные auto_increment ID прода не пересекались с пилотом. Внешние бизнес-ID
при этом остаются исходными. Импорт и зеркало используют один MySQL advisory lock.

## Запуск после установки кода и миграции 0052

```bash
cd /root/cm_stage/CM_V2
venv/bin/python scripts/import_gizmo_stage.py \
  --create-club 'Next, Уфа' --timezone Asia/Yekaterinburg \
  --branch-id 1 --cash-methods=-1,-2 \
  --date-from 2026-09-29 --date-to 2026-10-06
```

По умолчанию dry-run: никакой записи в БД. После сверки результата тот же запуск с
`--apply` создаёт выключенный пилот и импортирует данные. Повторный запуск переиспользует
его ID и обновляет записи без дублей. Можно передавать `--club-id` вместо создания.
Скрипт проверяет путь, APP_ENV=stage, stop marker и различие БД с продом.
Ключ вводится скрыто при каждом ручном запуске. Сертификат ранее подтверждён владельцем,
лежит в `/root/gizmo-stage-check/server.pem`. Секрет и персональные поля не печатаются.

Период от включительной начальной до исключительной конечной даты в UTC, максимум 31 день.
`users` и `hosts` читаются полностью. У `/sessions` нет DateFrom/DateTo по спецификации,
поэтому обе истории сессий читаются целиком и затем отбирается период; это пилотный
импорт, не оптимизированный периодический worker. Прогресс печатается по страницам.
`--without-sessions` разрешает явно ограниченный импорт, но не делает аналитику визитов готовой.

## До включения обслуживания

1. Сверить несколько известных визитов с интерфейсом Gizmo: время, ПК, пересадки,
   паузы и связь учётной сессии с usageSessionId. Факт доступности полей ещё не доказывает
   корректность расчёта всех сценариев.
2. Сверить реальные пополнения наличными/картой, бонусы и отмены, подтвердить способы оплаты.
3. Проверить полноту истории и счётчик сессий без usageSessionId/времени. Разобрать исключения.
4. Проверить пилот в модуле и показ времени в отчётах; вне пульса есть старые компоненты
   с привязкой к московскому времени, они требуют отдельной проверки для Уфы.
5. Доработать инкрементальную загрузку, сверку отмен, ограничения функций и выдачу наград
   после подтверждения семантики данных. Только потом поднимать integration_ready.

На момент подготовки кода подтверждены только образцы API и локальные тесты.
Установка на сервер, полный dry-run и фактический импорт требуют отдельного результата запуска.
