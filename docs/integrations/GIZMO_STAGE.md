# Gizmo v3 — пилот Next, Уфа

Пилот предназначен только для `/root/cm_stage/CM_V2` и отдельной базы stage.
Прод не меняется. Секретов в репозитории нет. Обслуживание пилота остаётся выключенным;
рассылки, награды и запись денег в Gizmo не включаются. Периодическая синхронизация
настраивается отдельно и только для явно выбранного stage-пилота.

## Проверено на API 6 октября 2026

Gizmo 3.0.92, HTTPS с проверенным сертификатом и именем `gizmo.local`,
филиал `NextClub`, branch ID 1, один филиал в ответе. Его timezone API возвращает
`Asia/Yekaterinburg`. Ключ передаётся через X-API-KEY. С действующим ключом
`system/version`, `branches`, `hosts`, `users`, `paymentmethods`,
`deposittransactions`, `sessions`, `usersessions` возвращают успешные ответы.
Следующие страницы hosts/users/deposittransactions/sessions/usersessions также проверены.
Реальный `nextCursor` — непрозрачная строка, хотя OpenAPI описывает объект.
`reports/sessionslog` возвращает HTTP 403 даже с новым ключом. Причина политики
доступа не установлена; импорт использует два доступных метода сессий.

Диагностика 6 октября: из 362 сессий периода `usageSessionId` ведёт к другому
пользователю в 359 случаях; в остальных трёх отличается длительность.
По одинаковому `id` пользователь совпадает в 362 случаях, а во всех восьми
сохранённых примерах совпадает и `span`. Поэтому пилот проверяет для КАЖДОЙ
завершённой сессии одинаковые id, userId, конечный неотрицательный span и
терминальное состояние (Ended/Moved). Несовпадение останавливает всю выгрузку
до записи. Это наблюдаемое поведение этой установки, не универсальная гарантия
Gizmo API; перед включением обслуживания нужна сверка с интерфейсом клуба.
Незавершённые сессии пропускаются со счётчиком: их длительность меняется между
чтениями. Смещение ID арифметикой и запасное сопоставление по usageSessionId запрещены.

## Единый формат

| Gizmo | Таблица модуля | Правила |
|---|---|---|
| users, Type=0, Model.Id | guests | guest_id = внешний ID, область уникальности club_id + guest_id |
| FirstName/LastName, MobilePhone/Phone | guests.fio/phone | Нормализация телефона, не связывать гостей разных клубов по ID/телефону |
| RegistrationDate/BirthDate | guests.date_insert/birth_date | Время регистрации UTC; день рождения календарной датой |
| hosts.Model.Id/Name/Number | club_pc_names | Стабильный uuid `gizmo:<ID>`; ручные названия и порядок не перезаписывать |
| sessions + usersessions | guest_sessions | Пилот Next 3.0.92: одинаковый id + userId + точный span; только завершённые; ПК из hostId |
| sessions.id/startTime/endTime | guest_sessions.id/date_start/date_stop | ID учётной сессии; UTC; не выдумывать окончание активной сессии |
| deposittransactions | guest_balance_topups | Только Deposit, выбранный branch, явно сопоставленные денежные способы оплаты |

События хранятся как DATETIME в UTC (как ожидает `guest_pulse.load_sources`);
локальное время Уфы используется при показе/расчёте пульса. Не прибавлять 5 часов в БД.
Sex — числовое поле на реальном сервере, но значения не объяснены в спецификации:
пол пока не выводим из номера. Type=1 users — общие/гостевые аккаунты, не персональные
CRM-профили. Удалённым/отключённым зарегистрированным пользователям телефон не импортируем.

Cash (-1) и Credit Card (-2) найдены в справочнике. Points (-4) и Deposit (-3)
не трактуем как новые деньги гостя. Для запуска нужно явно указать денежные методы.
Charge/Withdraw/Credit и isVoid не превращаются в положительное пополнение.
Отмена isVoided обновляет сумму ранее импортированного пополнения до нуля.
Повтор периода нужен для обнаружения отмен; постоянная сверка старых отмен ещё не включена.

Не импортируем `operations_log`: экономический смысл всех списаний и продаж ещё
не сопоставлен с категориями Langame. Нельзя считать пустой журнал отчётом о нулевых продажах.
Не используем изменение баланса в качестве пополнения. Внешние начисления не реализованы.

## Изоляция

`clubs.integration_provider`: langame (default для существующих) или gizmo.
`integration_ready=0` блокирует включение обслуживания Gizmo из админки.
Система не редактируется переключателем для уже заполненного клуба.
`club_integrations` хранит внешний филиал, источник/период и время импорта, без API-ключа.
Смена источника, филиала или пространства ID сессий после импорта запрещена.

Langame jobs явно пропускают Gizmo. Stage mirror сохраняет записи клубов с другим
provider в таблицах с club_id. При пересечении club_id с продом останавливается до
удаления данных. Суррогатные id pilot topups/PC names выделяются отрицательными, чтобы
новые положительные auto_increment ID прода не пересекались с пилотом. Внешние бизнес-ID
при этом остаются исходными. Импорт и зеркало используют один MySQL advisory lock.

## Запуск после установки кода и миграции 0052

```bash
cd /root/cm_stage/CM_V2
venv/bin/python scripts/import_gizmo_stage.py \
  --create-club 'Next, Уфа' --timezone Asia/Yekaterinburg \
  --branch-id 1 --cash-methods=-1,-2 \
  --date-from 2026-09-29 --date-to 2026-10-06
```

По умолчанию dry-run: никакой записи в БД. После сверки результата тот же запуск с
`--apply` создаёт выключенный пилот и импортирует данные. Повторный запуск переиспользует
его ID и обновляет записи без дублей. Можно передавать `--club-id` вместо создания.
Скрипт проверяет путь, stop marker, различие БД с продом и совпадение загруженных настроек с .env стейджа.
APP_ENV не определяет место запуска: на стейдже допустим и production-режим Flask с secure cookies.
Ключ вводится скрыто при каждом ручном запуске. Сертификат ранее подтверждён владельцем,
лежит в `/root/gizmo-stage-check/server.pem`. Секрет и персональные поля не печатаются.

Период от включительной начальной до исключительной конечной даты в UTC, максимум 31 день.
`users` и `hosts` читаются полностью. У `/sessions` нет DateFrom/DateTo по спецификации,
поэтому обе истории сессий читаются целиком и затем отбирается период; это пилотный
импорт, не оптимизированный периодический worker. Прогресс печатается по страницам.
`--without-sessions` разрешает явно ограниченный импорт, но не делает аналитику визитов готовой.

## До включения обслуживания

1. Сверить несколько известных визитов с интерфейсом Gizmo: время, ПК, пересадки,
   паузы и соответствие учётной и пользовательской сессий. Факт доступности полей ещё не доказывает
   корректность расчёта всех сценариев.
2. Сверить реальные пополнения наличными/картой, бонусы и отмены, подтвердить способы оплаты.
3. Проверить полноту истории и счётчики сессий без времени и незавершённых сессий. Разобрать исключения.
4. Проверить пилот в модуле и показ времени в отчётах; вне пульса есть старые компоненты
   с привязкой к московскому времени, они требуют отдельной проверки для Уфы.
5. Доработать инкрементальную загрузку, сверку отмен, ограничения функций и выдачу наград
   после подтверждения семантики данных. Только потом поднимать integration_ready.

Код пилота и миграция 0052 установлены на stage. Первый импорт остановился до
записи из-за ошибочного сопоставления usageSessionId. Исправление сопоставления
проверено локально; успешный фактический импорт требует результата следующего запуска.


## Пульс выключенного пилота

Обычный worker пульса пропускает выключенные клубы. После импорта запускается
отдельный stage_gizmo_preview: проверка пути/отдельной БД/маркера исходящих,
затем только Gizmo с service_enabled=0 и integration_ready=0.
Он заполняет текущий пульс по имеющимся завершённым визитам, включая гостей без Telegram.
Гости без загруженных визитов не входят в пульс. История оценок, реконструкция
прошлых дней и события переходов не создаются из частичной недельной выборки.
Обслуживание не включается. Для пересчёта без повторной загрузки API:

```bash
venv/bin/python scripts/rebuild_gizmo_stage_pulse.py --club-id 900001
```


## Полная история и регулярное обновление

`scripts/sync_gizmo_stage.py --club-id 900001` читает весь доступный справочник
и всю доступную API историю (без искусственной начальной даты). Сохраняются только
завершённые сессии зарегистрированных гостей с известным ПК и проверенным соответствием.
Общие аккаунты/неизвестные гости, неизвестные ПК и незавершённые сессии учитываются
в отдельных счётчиках пропусков. Отсутствующее/неверное соответствие двух методов
останавливает сбор до сохранения. При завершении игры между чтениями двух списков
проверяется актуальное состояние через GET той же usersessions/{id}.

У sessions нет документированного DateFrom/DateTo, поэтому текущий worker делает
полную сверку, а не заявляет инкрементальную выборку. Таймер запускается через 30 минут
после окончания предыдущего запуска; лимит чтения 200000 записей на ресурс,
лимит запуска 60 минут. Для выросшей истории потребуется отдельная оптимизация.
Сверка всех пополнений обнаруживает isVoided у старых операций. Исчезнувшие из API
записи автоматически не удаляются. Журнал продаж, снятия и начисления в Gizmo
этой задачей не подключаются. Ручной недельный импорт остаётся для диагностики;
после полной загрузки следует пользоваться full-history worker, чтобы сохранять
метаданные покрытия полной истории.

Настройка после обновления стейджа (не выполняет запись в Gizmo):

```bash
venv/bin/python scripts/configure_gizmo_stage_sync.py --club-id 900001
install -m 644 deploy/systemd/clubmodule-stage-gizmo@.service /etc/systemd/system/
install -m 644 deploy/systemd/clubmodule-stage-gizmo@.timer /etc/systemd/system/
systemctl daemon-reload
systemctl start clubmodule-stage-gizmo@900001.service
systemctl enable --now clubmodule-stage-gizmo@900001.timer
```

API-ключ вводится скрыто, проверяется запросом system/version и атомарно сохраняется
в `/root/gizmo-stage-check/sync-900001.json` (0600). В БД/Git ключа нет.
Worker отказывается читать доступный другим пользователям файл или symlink.
Файловый flock блокирует параллельные запуски worker; транзакция сохранения дополнительно
использует lock зеркала stage. История оценок/события не реконструируются автоматически:
пилот пересчитывает текущий пульс. Общие Langame jobs и ordinary Guest Pulse worker
по-прежнему не обслуживают выключенный Gizmo. Этот явно включённый stage worker —
исключение для проверки интеграции, а не новое поведение выключенных рабочих клубов.

Результат: `/root/gizmo-stage-check/status-900001.json`; статус complete означает,
что завершены и запись данных, и пересчёт пульса. При ошибке сохраняется предыдущий
last_success_at_utc. Ошибка после записи и до пересчёта дополнительно содержит
`data_saved_at_utc`; повторный запуск безопасен. Ошибки доступны в systemd journal.
Не подключаем новый вид задачи к продовым Telegram-алертам на этапе пилота.

Приостановка новых запусков и конфигурации:

```bash
systemctl disable --now clubmodule-stage-gizmo@900001.timer
venv/bin/python scripts/configure_gizmo_stage_sync.py --club-id 900001 --pause
```

Активный запуск не прерывается отключением таймера; конфигурация защищена тем же flock.
Если он ещё работает, дождаться окончания и повторить --pause.

### Почему ID 900001

Это внутренний ID временного пилота stage, не внешний branch_id (у Gizmo он 1).
Изоляция нужна из-за регулярного зеркалирования продовой БД. Нельзя присвоить пилоту
следующий низкий ID без общего резервирования: будущий продовый клуб может занять его,
и зеркало остановится на конфликте. На проде новый Gizmo-клуб может получить обычный
последовательный ID; перенос должен заново сопоставить club_id во всех его таблицах,
а не изменять только clubs. Текущий stage ID оставляем стабильным.


### Некорректные интервалы в старой истории

Сессии с endTime <= startTime явно исключаются из аналитики с отдельным счётчиком
`sessions_invalid_time_skipped`. Пустой/неизвестный часовой пояс и нарушения
сопоставления корректных по времени сессий всё ещё останавливают импорт.
Полный список исключений (ID, причина, начало/конец UTC, без имён/телефонов)
сохраняется в `/root/gizmo-stage-check/session-quality-900001.json` с правами 0600;
до 10 примеров также включаются в status. Такой интервал не заменяется выдуманной
длительностью. Если этот ID ранее был импортирован как корректный, его запись
удаляется только у текущего клуба в общей транзакции. Нормализатор сохраняет
строгую проверку, чтобы другие вызывающие не могли случайно записать такой интервал.
